# 接口改进计划与 Wiki 定位演练

状态：**设计演练 / 尚未实现接口改动**。日期 2026-10-14，业务代码基线 `8f55892`。本次交付是工程导航、影响分析和候选计划；不新增运行时接口、不承诺发版、不将提案记作完成。

## 原 Wiki 的实际表现

演练问题：“改进整个项目的外部接口、依赖接口、标签接口与接口规则，先定位，再提 plan。”

先仅阅读 Home、Architecture、Integration-and-API、Tags-and-ledger、Settings-and-external-data，再沿既有文档链接阅读 docs/architecture 与 CONTRIBUTING；此阶段没有做源码搜索。

| 子问题 | 原 Wiki 能回答 | 缺口 |
|---|---|---|
| 外部接口指哪层 | 五入口、HTTP 路由与客户端返回 null | 没有将公共 API 与外部源适配器分成任务路由 |
| 依赖接口在哪 | ports.ts、service.ts 与可选端口名称 | 缺逐个声明符号、必需/可选能力、失败与调用者矩阵 |
| 标签接口在哪 | tags/tagging/ledger 中主要函数 | 缺归一、模型建议、主题绑定、裁决、服务应用之间的改动传播路径 |
| 接口规则怎么改 | 贡献规则与原架构表覆盖版本/快照 | 缺规则对应位置、窄测试与迁移风险入口 |

判断：原文档适合了解项目，但还不够精细到“自然先用 Wiki 做工程计划”。主要问题是检索成本和影响信息分散，不是页数少。

本次作者已在此前读过代码，不能把本轮说成独立盲测。新增路由后做的是有记录的自测与定点核验。未来如需证明陌生执行者也会主动使用，应给未看过源码的执行者同样问题，只提供仓库入口，记录其实际路径；此项未做。

## 现在如何只用 Wiki 写第一版计划

从 [工程入口](Engineering-entry.md) 选择 public-api、external-source、host-ports、tagger-contribution、ledger-policy、compatibility，读 [接口影响地图](Interface-map.md) 对应节即可得到下面的候选计划。准备实施时必须按路由定点核对当前代码，不能用“不看源码”代替实现审查。

### P1：明确失败结果，保留旧客户端行为

- 目标：接入者能区分参数错误、缺端口、外部不可用，而不必将所有失败都解释成空集。
- 已知现状：服务 ServiceResult、HTTP 状态/error、客户端 data/null 分层；旧客户端丢弃详细错误。
- 候选方案：讨论新增结果式客户端方法或独立客户端选项，现有方法保留 data/null。具体命名、错误联合和重试元数据尚未确定，不写成已有 API。
- 位置：public-api 路由中的 ServiceResult / ServiceError、createEvidenceHandler、createEvidenceClient，以及 guards、features、公开入口与类型声明。
- 依赖：先确定失败分类与向后兼容策略，才确定 HTTP 与 SDK 的新形状；不依赖标签规则重写。
- 交付：错误映射表、兼容 API 设计、参数/形状/失败测试、类型消费者示例、CHANGELOG 与 API Wiki。
- 退出证据：旧客户端调用保持现有返回；新调用能区分各失败；网络/验形失败仍不会显示成零研究；安装包 CJS/ESM 与 TS 消费测试通过。

### P2：明确外部能力与宿主依赖的边界

- 目标：替换文献源或存储时，知道哪些能力可缺、如何降级、哪些保证由宿主负责。
- 已知现状：ExternalEvidenceSource 有必需和可选能力；预算在客户端实例内；host ports 抽象存储而不保证分布式事务。
- 候选方案：先做外部源与宿主端口的契约测试矩阵，覆盖“缺可选方法 / null / 空结果 / partial / 抛错 / 缓存失败”。共享预算、取消与超时如确有需求，再设计可注入端口；不先强制增加第三方依赖或共享预算实现。
- 位置：external-source、external-transport、host-ports；声明在 ports.ts，装配在 service.ts，外部请求在 openalex.ts。
- 依赖：能力降级测试可独立于 P1；若新增错误细分，等待 P1 确定分类后接入。
- 交付：能力/失败矩阵、适配器验收样例、必要的最小端口扩展设计、缓存与预算责任说明。
- 退出证据：缺可选方法仍有受支持的站内功能；外部失败不缓存成空结果；内存测试与真实 provider 测试分别记录；不宣称单实例额度等于全局硬预算。

### P3：打通模型、贡献包、账本与有效标签的可追溯规则

- 目标：换模型或规则时清楚哪些标签被接受、丢弃、争议或通过审核，避免建议直接进入统计。
- 已知现状：模型/贡献验形与账本裁决分开；null 置信度不是自动拒绝；存储召回必须包含账本新增标签。
- 候选方案：先补跨流程案例及明确的拒绝/丢弃原因映射，再决定是否给结果新增可选出处/诊断字段。是否拒收缺置信度、是否改信任顺序是独立政策决策，默认保持现行语义。
- 位置：tagger-contribution → ledger-policy → ledger-integration；标签键变更另经 tag-normalization 处理迁移。
- 依赖：作品 ID、标签键与现行裁决规则先确定，再定义跨流程诊断；可与 P2 的外部适配器工作独立进行。
- 交付：建议到有效标签的追溯例子、贡献输入兼容矩阵、裁决/召回/缓存案例、需变更时的键迁移设计。
- 退出证据：同级争议不计入、审核通过生效且禁止自审；账本失败不回退原始标签；仅账本新增标签可被查询召回；历史规则变更有显式迁移与行为说明。

### P4：统一接口变更交付规则

- 目标：上述改动能被接入者识别、升级和验证。
- 位置：compatibility、settings-contract，及 CONTRIBUTING、CHANGELOG、API/行为快照、manifest、五包入口。
- 顺序：每项方案评审时先列受影响的生产端/消费端，再确定是否改契约与版本；测试通过后审阅快照差异，最后更新共享 Wiki 对应小节。
- 交付：每项改动的兼容矩阵、必要迁移说明、可安装包、准确的源码/测试/Wiki 路由。
- 退出证据：类型、包导出、guard、展示词典、功能注册、快照与文档一致；旧接入方式的回归证据明确；未验证的真实服务行为保留为未知。

## 定点核验与 Wiki 更新方法

以上第一版方案由既有 Wiki 的边界推导，不依赖先猜一套新接口。之后路由工具只打开清单登记文件，要求声明行恰好命中一次，并核对文档锚点和测试路径。

这只能证明“位置可定位”，不能证明调用链语义：实施者仍须读取这些位置与相关内部调用。如果发现 Wiki 错误，先修对应路由与局部规则，不扩散到重写全站。

更新动作按实际改动选择：新增 API → public-api/compatibility；换数据源 → external-source；改归一 → tag-normalization + 迁移；改置信策略 → tagger-contribution/ledger-policy；改配置 → settings-contract。不要把工程提案写进“已实现”状态表。

本轮验证结果见[定位演练核验记录](Wiki-routing-verification.md)。
